## Security and anti-extraction controls

A public website cannot be made impossible to reverse engineer. Browser-delivered JavaScript, HTML, CSS, network requests, and rendered assets can be inspected by visitors. Minification and obfuscation raise effort but are not reliable security boundaries.

The engineering release policy is therefore:
1. Keep the source repository private while proprietary implementation is being protected. Public forks and copies already made cannot be recalled by changing visibility.
2. Keep proprietary algorithms, mission-analysis logic, credentials, signing keys, and sensitive datasets on controlled server-side services; never ship secrets or privileged keys in browser bundles.
3. Expose only authenticated, least-privilege APIs; validate requests server-side and apply rate limits, quotas, abuse detection, audit logs, and monitoring.
4. Use access controls, encrypted secrets, dependency and vulnerability scanning, backups, and a documented incident-response process.
5. Review production bundles and network traffic for accidental source maps, secrets, internal endpoints, debug routes, and unnecessary proprietary data.
6. Maintain dated releases, signed tags where feasible, source snapshots, commit history, contributor records, and evidence of authorship.
7. Have a qualified IP/security professional review proposed restrictions and enforcement in each target jurisdiction.
